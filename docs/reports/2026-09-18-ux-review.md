# UX review — סיגמה (Sigmatec Operations) kibbutz-cards redesign

Reviewed: design spec `docs/superpowers/specs/2026-09-17-kibbutz-cards-redesign-design.md` (§2–§7j) and the
approved mockup (`sigmatec-ops-mockup.html`, v6, 17.9.26). Scope: an evidence-based review with concrete,
opinionated recommendations, before chunk 0–7 implementation starts.

Context that shapes every recommendation below: 2 field technicians (אביאם, ניתאי) using this **outdoors, one
hand, on a phone, often mid-task at a meter cabinet** — the whole redesign lives or dies on "read fast, act
fast" for them. Everyone else (PM/CEO/dev/viewer) mostly uses it seated, so their screens get a lighter pass.

---

## 1. Top 10 recommendations (ranked by field-technician read/act speed)

### 1. The arrival flow has 3 screens before the CTA that matters — collapse it to 1 confirm tap
**Problem (spec §5.1, mockup `arrive`+`brief`):** cold start → arrival sheet (search + pick) → briefing screen
(tasks + bullets + visit) → tap 📍 סיכום ביקור. The spec already worries about this ("Target: visit form
visible within 2 taps from cold start") and adds an escape hatch (`ישר לסיכום ביקור →`), which is the right
instinct but treats the symptom, not the cause: the briefing screen itself has no reason to gate the CTA — the
CTA is *always* visible in the sticky footer already (`.stick` in the mockup), so the fix isn't adding a shortcut
link, it's making the default path shorter.
**Recommendation:** merge arrival-pick and briefing into one screen: the moment a kibbutz is picked from the
sheet, morph the sheet into the briefing in place (View Transitions, already in the stack) rather than
navigating to a second screen — same pattern as **Linear's command palette**, where "one thing selected → one
result state" beats a multi-screen wizard because "a three-click workflow with a 100 ms response at each step
can feel slower than a one-command workflow, because the user has to keep reorienting" ([Linear speed
breakdown](https://dev.to/0xgosu/why-linear-feels-fast-local-data-small-updates-and-product-discipline-1m53)).
Effort: **M** (briefing is already built per spec §5.1; this is a navigation/animation change, not new data).

### 2. Full EMS task descriptions on every card (spec §4, D5) will bury the thing the technician actually needs on repeat visits
**Problem:** spec explicitly decided "full text always, no line-clamp" for EMS task descriptions on the card.
The mockup's גבים card in the active-kibbutz view already shows a 200+ character description
("אובדן 15–20%... לבדוק חיבורי CT ומונים משניים בראשי") stacked under 3 meeting bullets — on a 390px phone this
is one card = most of a screen, before the technician even gets to the next kibbutz. This directly fights the
spec's own density goal ("one card ≈ 3 scrolls of thumb max," §6).
**Recommendation:** apply **progressive disclosure** — title + first line (≈70 chars) + metadata chips visible by
default, full description on tap/expand. This is exactly NN/g's prescription for cognitive-load reduction in
information-dense mobile UIs: "employ progressive disclosure to defer secondary options... which focuses users'
attention on the primary options" ([NN/g, Progressive
Disclosure](https://www.nngroup.com/videos/progressive-disclosure/); [4 principles to reduce cognitive
load](https://www.nngroup.com/articles/4-principles-reduce-cognitive-load/)). Keep "full always" only in the
**briefing** screen (§5.1), where the technician has already committed to one kibbutz and wants everything —
that's the right place for density, the card grid is not. Effort: **S** (CSS/markup truncation + expand
affordance; no data change).

### 3. Bottom nav's 5th slot ("עוד/⋯") hides too much load-bearing stuff behind one generic icon
**Problem (spec §6, mockup nav):** 🏘 · 📍 · 🚚 · 📦 · ⋯. But `⋯ עוד` is the entry point for feedback (§7),
settings (§7h), personal gaps (§7h), holidays admin, and — critically — is also where `📅 נוכחות` and `🗓 יומן`
and `✅ משימות` presumably live (not shown in the phone nav at all in the mockup, only accessible via the "att"
and "tasks" screens directly). For a field tech checking "did I log today's attendance," that's now 2 taps
through an unlabeled overflow menu instead of a primary destination.
**Recommendation:** Material 3 caps a nav bar at 3–5 *destinations*, not a junk drawer — "provide access to
three to five destinations... each represented by an icon and label" ([M3 Navigation
bar](https://m3.material.io/components/navigation-bar/guidelines)). Sigma already uses all 5 slots for the
truly daily actions (קיבוצים/ביקור/תעודה/מלאי is right), so keep ⋯ but make it a **menu sheet with clear
labeled rows** (not a second nav), and add unread-style badges only for things that need attention today
(gaps, unread feedback replies) — do not use ⋯ as a dumping ground for a 6th primary flow like נוכחות, which
technicians touch daily. Effort: **S** (information architecture / menu contents, no new components).

### 4. The 2-hour push reminder is the single highest-leverage screen in the whole spec and it's built almost perfectly — one gap: no in-app equivalent for the day someone doesn't see the push
**Problem (spec §5.2):** great decision to make copy positive-only and rotate 16 variants, single nudge — this
matches Apple's own guidance that feedback should reinforce, not nag, and that a system shouldn't over-notify
("long-running haptics... dilute the meaning... distract people," generalizes to notification fatigue —
[Apple HIG,
Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback)). But pushes are dropped
silently on Android battery-optimized devices and on iOS PWAs with notifications not yet granted (a real risk
here — §7h's own "🔔 התראות" state includes "לא נתמך" as an expected state). If the push never arrives, there's
no fallback and the gap silently rolls into `gapsFor()` (§7h) a day later — invisible to the technician until
someone else notices in a report.
**Recommendation:** surface the same nudge as a **passive banner card at the top of the קיבוצים home screen**
("💪 <קיבוץ> — עוד לא סיכמת, 2 שעות") the moment the timer fires, regardless of push delivery — this is the
"offline/undelivered-notification-safe" pattern field-service apps use because field connectivity is
unreliable by design ("offline-first... intelligent data priming... to finish work regardless of network
connectivity" — [Salesforce Field
Service](https://help.salesforce.com/s/articleView?id=release-notes.rn_fieldservice_242_mobile_lwc_overview.htm)).
Effort: **S** (reuse `gapsFor()` logic already specced for §7h, render one extra card).

### 5. Delivery-cert gate has zero visual urgency until save-time, when it becomes a hard block
**Problem (mockup `visit` screen, `.certchip`):** the cert-required warning chip sits mid-form, same visual
weight as any other row, styled like a status label not a blocker. A technician who fills the whole form (day
type, hours, products, notes) only discovers the save is gated at the bottom button — a classic "error at the
end" pattern that Baymard flags as one of the biggest form-abandonment causes: field-level and contextual
validation, not end-of-form rejection, drives completion — Baymard's own mobile-checkout research shows
completion improves substantially when constraints are visible where the decision is made, not after
([Baymard, Form Design](https://baymard.com/learn/form-design)).
**Recommendation:** move the cert chip to pin directly under the product checklist (already the trigger for the
requirement) with a persistent sticky-footer state change — e.g. the primary "שמור סיכום" button itself
relabels to "🚚 הפק תעודה ← שמור" the instant a product is checked, so the technician sees the two actions
fused as one flow instead of discovering a hidden second requirement. This preserves the exact gating logic in
`09-visits.js` (spec explicitly says don't touch it) — it's a presentation-only fix. Effort: **S**.

### 6. Search/filter crossfade is a nice touch, but the meeting-bullet ➕→🔗 "morph" risks being a4 dead-end pattern with no undo
**Problem (spec §3.3, mockup `.bl .act`):** tapping ➕ opens `emsTaskModal` prefilled from the bullet; on success
the row permanently becomes 🔗 with no visible route back if the task was created by mistake (e.g., wrong bullet
tapped, wrong assignee). The ✓ long-press "mark done" has an explicit undo (§3.3) but the ➕→🔗 conversion does
not.
**Recommendation:** give the 🔗 state the same secondary-menu undo as done-marking: long-press → "בטל קישור"
(does not delete the EMS task, just unlinks `ems_task_id` so a second ➕ can be issued). This matches the
optimistic-UI discipline the rest of the spec follows well (undo-toast on stock counts, §"מלאי"): "your undo
must be reliable, obvious, and fast... show the result as if it succeeded but with a quiet hedge" ([Optimistic
UI patterns](https://rohanshewale.me/blog/2025/11/optimistic-ui-patterns/)). Effort: **S**.

### 7. Card grid mixes cognitively different "read" content (meeting bullets) and "act" content (EMS tasks) with identical visual weight
**Problem (mockup, e.g. גבים card in `cards` screen):** meeting bullets (read-only history, muted dot list) and
EMS tasks (actionable, has assignee/due/priority) sit in two boxes of near-identical size/border/background —
`.meet` and `.ems` differ only in a dashed top border vs a tinted background. On a quick scroll a technician
scanning "what do I need to *do* here" has to read both blocks fully to tell them apart.
**Recommendation:** borrow the field-service convention of a hard visual split between "context" and
"work-to-do": Housecall Pro's mobile job screen is rated ahead of competitors specifically because it
"features large tap targets, minimal navigation depth, and a workflow that surfaces what techs need without
making them dig" ([technician's comparison of Jobber vs Housecall
Pro](https://korekomfortsolutions.com/will-my-guys-actually-use-it-a-technicians-view-of-jobber-vs-housecall-pro-mobile-apps/)).
Concretely: give the EMS-task block a colored left rail per priority dot (already exists) *and* pull it visually
above the meeting bullets — action before history — with the bullets collapsed to the latest 1–2 lines and
"עוד N" instead of always-expanded. Effort: **S–M** (reorder existing blocks + collapse rule).

### 8. Dev-page rail (`.rc` vertical chips) uses `writing-mode: vertical-rl` text for column names — reads badly on Hebrew and is a poor RTL/accessibility choice
**Problem (mockup CSS `.rc{writing-mode:vertical-rl}`):** rotating Hebrew text 90° for the collapsed-column
rail is unusual even for LTR UIs and Hebrew has no native tradition of vertical text (unlike CJK, where
`vertical-rl` is a real reading mode) — this will just look like sideways Latin-script styling misapplied to
Hebrew, hurting both legibility and the "RTL correctness is a release gate" principle the spec itself sets
(§6). This is a desktop-only screen (dev/PM audience) so the effort-to-harm ratio is small but it's an easy,
free fix.
**Recommendation:** keep the rail horizontal — a slim horizontal strip of pill-chips (name + count + dot),
wrapping if needed, rather than rotated text. Effort: **S**.

### 9. The complaints/voice box's Web Speech API path has no offline or permission-denied fallback state shown in the mockup
**Problem (mockup `fb` screen, spec §7):** the `.live` "מקליט ומתמלל…" state assumes speech recognition just
works. Android Chrome mic permission can be denied, and Web Speech API silently fails/returns empty on some
networks (it round-trips to Google's servers even for "live" recognition) — a technician in a kibbutz field
with weak signal is the worst-case user for this exact feature.
**Recommendation:** the spec already speced the MediaRecorder+Whisper fallback for iOS Safari (good) — extend
the *same* fallback trigger to "no result after 3s" or "permission denied" on Android too, not just
platform-detection, so a bad-signal Android device degrades gracefully instead of looking broken. Effort: **S**
(the fallback code path already exists per spec §7 ladder; just widen the trigger condition).

### 10. No stated skeleton/loading state for the two things that are slowest on a field connection: EMS cache sync and the arrival-sheet kibbutz list
**Problem:** spec §6 lists "skeleton shimmer while loading" as a micro-motion item but doesn't say *where* —
the mockup shows the arrival sheet and card grid fully populated in every screenshot, with no loading state
shown for either. On a kibbutz's typically weak cellular signal, EMS cache sync (`13-ems.js`) and the
`field_checkins`-ordered arrival list are exactly the two data fetches most likely to be visibly slow.
**Recommendation:** explicitly spec skeleton rows (not spinners) for both: the arrival sheet's kibbutz buttons
and the card grid's EMS-task blocks. This is not cosmetic — NN/g and independent studies found users perceive
skeleton-screen loads as meaningfully faster than spinners for identical load times ("users perceived pages
with skeleton screens as loading faster than identical pages with spinners, even when measured load time was
exactly the same" — [NN/g, Skeleton Screens vs. Progress Bars vs.
Spinners](https://www.nngroup.com/videos/skeleton-screens-vs-progress-bars-vs-spinners/)). The `.sk` CSS class
already exists in the mockup — this is a "use it everywhere data can be slow" instruction, not a new build.
Effort: **S**.

## 2. Per-screen notes

**Cards home (phone + desktop).** Region sub-headers are correctly subtle (spec §7c requirement met — thin
label + hairline, not a colored bar). The section-then-region-then-alphabetical hierarchy is sound information
scent, matching how a PM actually thinks about the territory. Risk: with 44+ cards and only 2 top-level
sections, "🆕 לקוחות חדשים" at only 8 cards will feel like an afterthought above the 36-card "✅ פעילים" — fine,
that mirrors reality (8 new vs 36 active), no fix needed. The quick-action row (📍/🚚/🗓, spec §3.3) is the
single best decision in Part A — it turns every card into a one-tap dispatcher instead of a read-only tile;
make sure it survives on cards with 3+ EMS tasks without the row being pushed off the visible first-scroll area
(currently at risk per recommendation #2/#7 above).

**Arrival sheet + briefing.** See recommendation #1. One more gap: "לא בקיבוץ היום" dismisses *for the day* per
spec, but the sheet reappears "when the app opens and there is no check-in today" — if a technician opens the
app 5 times before deciding, do they see the sheet 5 times or does the dismiss persist across app opens that
same day? Spec doesn't say; assume persist-per-day (store the dismissal like the check-in), otherwise this
becomes an annoying re-ask exactly on the days it's least wanted.

**Visit summary.** Numeric step-counters (`+`/`−`) for quantities are the right mobile pattern over a text
input (matches Baymard's guidance that "the entire field serving as the touch target rather than just the
input box" and 48dp minimums) — good. The `<bdi>` isolation around quantities/codes (mockup already does this,
e.g. `<bdi>38</bdi>`, `<bdi>E360CT-3P</bdi>`) is correctly applied and is exactly the RTL bidi guidance ("even
in RTL languages, numbers are written left-to-right... bidi" — [RTL/Bidi
guide](https://www.translatedright.com/blog/designing-for-rtl-languages-in-mobile-apps-a-complete-guide-to-right-to-left-development/)).
See recommendation #5 for the cert-gate placement fix.

**Attendance.** The month-grid color coding (filled/office/missing/weekend/holiday) is dense and scannable —
good match for "a month at a glance" goal (spec §7e). One contrast risk: `.mth .d.h` (holiday) uses a light
violet-on-white badge at small size — verify this meets 4.5:1 in both themes, violet-on-pale-violet is a common
low-contrast trap. The "היום" card surfacing the day's check-in ("ביקור היום: גבת... יום שטח יסומן אוטומטית")
is a strong automatic-fill decision that removes a whole manual step — keep it.

**Inventory + stock change.** The "no free-text correction, every change routes through visit/order/recount"
rule (spec, `inv` screen note) is the single strongest inventory-integrity decision in this spec — it maps
directly to the field-service best practice of tying every stock movement to a source-of-truth event rather
than a manual adjustment field, which is exactly what prevents the "phantom shrinkage" problem these tools
usually have. The recount flow's mandatory comment + auto-notify (עידן/עמיחי) is good friction (intentionally
slows down the one dangerous action). No changes recommended here — this section is well-designed as spec'd.

**Calendar + route.** The "מסלול היום" drag/arrow reorder with derived headers (🌅/➡️/🌇/📥) is a nice touch that
avoids a free-text field nobody would fill in consistently — good design instinct (spec explicitly rejected
free-text headers, correctly). Watch one thing: the day-panel's "➕ שבץ משימות" (schedule) and the route
reorder live in the same panel — on mobile this is a lot of interactive surface in one bottom sheet (search +
multi-select + drag list); consider splitting scheduling into its own sheet layered on top rather than
inline, so the drag-reorder gesture space doesn't compete with tap targets for the scheduler checkboxes.

**My tasks.** Straightforward priority-first grouping (overdue → this week → no-date), matches Things
3/Todoist's "today view" convention of surfacing urgency before category. Good as spec'd.

**Dev page.** See recommendation #8 (vertical rail text). The flow-strip-as-mini-Sankey is a nice glanceable
summary for the CEO/PM audience — appropriate to keep "more colorful" per עידן's explicit direction, this is
the one screen where that's the right call because color *is* the data here (status), unlike the field
screens where color is decoration.

**Settings / gaps / day-log / usage.** "📋 הפערים שלי" (personal gaps, §7h) is a strong pattern — turning
scattered nag logic (missing attendance, missing visit, overdue task) into one prioritized, one-tap-resolves
list is the same idea as Todoist/Things "Today" smart lists, applied to compliance gaps instead of tasks. Usage
analytics (§7j) is admin-only and low-risk from a field-tech UX standpoint; one caution — the "usageNarrative"
sentences risk reading as surveillance ("ניתאי לא השתמש בעמוד המשימות כלל השבוע") if ever seen by anyone but
עידן; keep this strictly עידן-only as spec'd, and keep it out of any shared digest.

**Feedback.** See recommendation #9 (speech-to-text fallback trigger). The kind-toggle (💡/🐞/😠) plus anonymous
option is well-scoped; the GitHub-issue-from-bug-report bridge (§7) is a good closed loop — most feedback
tools lose bug reports in an inbox that nobody re-visits, wiring straight to the dev board avoids that.

## 3. RTL & Hebrew specifics

- **Numbers/codes/dates in `<bdi>`:** already systematically applied in the mockup CSS and markup
  (`<bdi>38</bdi>`, product codes, dates like `<bdi>3.25</bdi>`) — correct, keep the contract test that greps
  for un-isolated numeric runs.
- **Icon mirroring:** the spec correctly calls for `rtl:` Tailwind variants on directional icons (chevrons,
  back). Verify this against the actual icon set used — Lucide's `chevron-left`/`chevron-right` map to visual
  direction, not semantic direction, so in RTL "back" must resolve to the icon that *looks* like it points
  toward the reading-start side (right edge in RTL) — this is the single highest-frequency RTL bug class per
  general guidance ("icon mirroring is one of the highest-frequency RTL bugs" — [RTL layout testing
  guide](https://placeholdertext.org/blog/the-complete-guide-to-rtl-right-to-left-layout-testing-arabic-hebrew-more/)).
  In the mockup, `chevron-right` is used for "back" in several header back-buttons (`fb`, `newk`, `visit`,
  `sched` screens) — confirm this renders as pointing toward the reading-start (right) side, which is correct
  for RTL back-navigation, but audit every other chevron usage (day-panel prev/next month arrows, `.stop .ar`
  up/down) individually rather than assuming one rule covers all of them.
- **Logos, codes, product SKUs stay LTR:** correctly not mirrored anywhere observed (`E360CT-3P`, `Robustel
  R1520` render untouched) — matches guidance to mirror directional elements only, never logos/codes/URLs.
- **Typography for outdoor readability:** base 15px (mockup `body{font-size:15px}`) is on the low side for
  a screen a technician glances at in direct sun while standing at a meter cabinet — recommend bumping the
  task/bullet primary text to 16–17px minimum (the visit-form textarea already uses `font-size:15px` — bump
  that too) and favoring **Assistant's 600–700 weights for anything read outdoors**, not 400, since "bold
  typography, high-saturation colors... avoid thin fonts" is the standing outdoor-legibility guidance
  ([sunlight readability
  guidelines](https://www.panniergraphics.com/blog/letter-height-visibility-chart-for-outdoor-sign-readability)).
  This doesn't require redesign — it's a token change (`--font-size-base: 16px`, task/bullet text weight 600).
- **Contrast in sunlight:** several mockup badges use soft-tint-on-tint combinations (`.badge.b` turquoise text
  on turquoise-tinted background, `.badge.w` amber-on-amber-tint) that are already borderline at ~3:1 indoors —
  outdoors in direct sun these will likely wash out below readable contrast. Sunlight-readability research puts
  the practical minimum around 5:1, not the indoor WCAG-AA 4.5:1 floor ("reasonable readability starts at an
  effective contrast ratio of 5" — [sunlight readable displays
  research](https://riverdi.com/blog/sunlight-readable-displays-the-most-important-parameters-of-outdoor-lcd-displays-you-need-to-know)).
  Recommend re-checking every `*-soft` badge combination against 5:1, not 4.5:1, specifically because this is
  an outdoor-use app.
- **One-handed reach / target sizes:** the spec already sets 56px arrival-sheet buttons and ≥44px general /
  ≥56px primary touch targets (§6) — good, matches both Material 3's 48dp minimum and Baymard's finding that
  sub-48dp targets measurably hurt completion ("mobile forms with 48dp input fields... show 40–50% higher
  completion rates" — [Baymard touch target
  research](https://baymard.com/learn/form-design)). The one place this isn't yet stated: the `.bl .act` bullet
  action button (➕/🔗) in the mockup CSS is `width:30px;height:30px` — below the 44px floor, and it's a
  frequently-tapped control (spec §3 makes this the primary bullet→task conversion action). Recommend bumping
  to at least 40×40 visual with a 44×44 invisible hit-area padding, the standard "small icon, big tap zone"
  technique.
- **Reach zone for the bottom nav's raised center button:** the `.nav a.big` (📍 ביקור) sits higher than the
  bar (`margin-top:-16px`) which is good thumb ergonomics (closest point to a relaxed one-handed grip), but
  make sure it doesn't collide with the browser/PWA gesture-nav bar on Android — test on a real device with
  3-button nav *and* gesture nav, both are common in the Israeli Android install base.

## 4. Motion & feedback

**Where motion helps comprehension (keep these):**
- Card filter crossfade (fade-out leaving / fade-in entering, staggered) — makes the *set change* legible
  instead of a jarring re-layout; this is exactly what `AnimatePresence`/Motion crossfades are for.
- Bullet→🔗 morph on task creation — turns an otherwise invisible state change (a DB write) into a visible
  confirmation, which is the correct use of motion as *feedback*, not decoration.
- Sheet spring-in (320ms) — signals "this is a temporary layer, will go away" which is the right semantic for
  a bottom sheet vs. a full navigation.
- Skeleton shimmer — see recommendation #10; extend its usage rather than change its design.

**Where motion should be trimmed or is a risk:**
- The card crossfade + a simultaneous `gsap.from` stagger-in on tab-switch (mockup JS, `tabs` click handler)
  layers two animation systems (GSAP tween + the filter crossfade) on the same cards — the code comment itself
  flags this was already a source of a bug ("a second overlapping 'from' tween froze cards at opacity 0"). This
  is a real signal to consolidate to **one** animation system driving card enter/exit, not two competing ones,
  before this ships to production.
- BorderBeam/ShimmerButton (Magic UI, spec §7c) on every primary CTA and every new/edited card risks constant
  low-level motion competing for attention exactly where the technician needs to *read*, not be drawn away by
  motion — reserve these for genuinely rare events (first-time card creation) not routine states.
- `prefers-reduced-motion` is correctly respected everywhere observed in the mockup CSS
  (`@media (prefers-reduced-motion:reduce){*{animation:none!important}}`) — keep this as a hard gate, not a
  soft preference, for every future animation added outside the current set.

**Haptics:** not mentioned in the spec at all. For a phone-first field app, a light haptic tap on: check-in
confirm, visit save, and the cert-gate block would reinforce success/failure without requiring the technician
to look at the screen — Apple's guidance is to use haptics "to reinforce actions and events" but keep them
optional and non-fatiguing ([Apple HIG,
Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback)). Recommend adding
`navigator.vibrate()` (Android; iOS PWA has no haptics API, accept the gap) on save-success and the cert-block,
gated behind the same reduced-motion-style user preference, effort **S**.

**Optimistic UI / offline states:** the spec's stock-recount flow correctly shows the computed diff instantly
before save (`badge r`, "שינוי −3" in the mockup) — good optimistic pattern. Two gaps:
1. No visible "offline" chrome anywhere in the mockup — no banner, no disabled-state styling for
   connectivity-dependent actions (cert issuing explicitly requires connection per spec §5.1 rule 4, "offline →
   the existing guidance alert" — but that's reactive, shown only after the user tries). A field app should show
   connectivity state proactively (a small dot/chip in the header, not just error-time alerts), matching the
   offline-first discipline field-service tools are built around.
2. The arrival check-in and visit-form save should both be optimistic (write locally, sync in background,
   toast on conflict) given the whole premise of this app is technicians working in low-signal kibbutz
   locations — worth stating explicitly as a requirement for chunk 5, not left implicit.

## 5. Anti-patterns to avoid

- **End-of-form validation surprises** (cert gate, recommendation #5) — Baymard's mobile checkout research is
  unambiguous that discovering a blocking requirement only at submit time is a top abandonment driver
  ([Baymard, Form Design](https://baymard.com/learn/form-design)); Sigma should surface every hard gate at the
  point of the triggering action, not at save.
- **Junk-drawer overflow menus** (recommendation #3) — cramming daily-use destinations behind a generic "⋯"
  violates Material 3's own nav-bar scope guidance and just relocates the discoverability problem instead of
  solving it ([M3 Navigation bar](https://m3.material.io/components/navigation-bar/guidelines)).
- **Spinners for anything longer than ~300ms** — replace with skeletons everywhere per recommendation #10;
  spinners measurably read as slower for identical wait times ([NN/g skeleton
  research](https://www.nngroup.com/videos/skeleton-screens-vs-progress-bars-vs-spinners/)).
- **Motion for motion's sake on every card/button** — the spec's own library list (BorderBeam, ShimmerButton,
  Spotlight, background-beams) is a lot of simultaneous "flourish" libraries for an app whose primary user reads
  it in bright sun while standing; use them sparingly (as the spec itself says, "restrained") and audit after
  chunk 4 whether they still feel calm at real screen brightness outdoors, not just on a dev monitor indoors.
- **Un-mirrored or wrongly-mirrored directional icons** — the single most common Hebrew/RTL regression class;
  needs a manual pass per icon usage, not a blanket CSS rule, since some (SKUs, media controls) must stay
  un-mirrored.
- **Treating a rotated-text pattern borrowed from CJK vertical writing as if it applies to Hebrew** —
  recommendation #8; Hebrew has no vertical-text reading tradition, `writing-mode:vertical-rl` on Hebrew labels
  is a foreign pattern with no readability upside here.

## 6. UX principles for סיגמה — pin this

1. **Field tech first.** Every screen decision defaults to "what does אביאם/ניתאי need standing outdoors,
   one hand, mid-task" — office/desktop screens get a lighter design pass.
2. **Action above history.** EMS tasks (do) sit above meeting bullets (context) on every card — never equal
   weight.
3. **Show the gate before the wall.** Any hard requirement (cert before save, energy locked to עידן) is visible
   at the triggering step, never discovered only at submit.
4. **One thumb, one tap.** Primary actions ≥56px, everything interactive ≥44px, reachable in the bottom third
   of the screen.
5. **Skeletons, not spinners.** Every fetch that can be slow on kibbutz signal gets a shaped placeholder, never
   a bare spinner.
6. **Progressive disclosure over "show everything."** Cards show a scannable summary by default; full detail is
   one tap away in the briefing/modal, not baked into every list row.
7. **5:1 contrast, not 4.5:1 — this app is read in direct sun.** Recheck every soft-tint badge against that
   bar, not the indoor WCAG floor.
8. **Motion explains state changes, it doesn't decorate.** If removing an animation wouldn't lose information,
   cut it; always respect `prefers-reduced-motion`.
9. **Mirror direction, not identity.** Flip chevrons/arrows/back; never flip SKUs, codes, logos, or numbers —
   audit per icon, not by blanket rule.
10. **Undo everything reversible, confirm everything that isn't.** Task-links, bullet-done, and stock counts
    get undo; cert issuance and deletions get an explicit confirm.

## 7. Navigation & layout inspiration from well-known management apps

Follow-up (עידן, 18.9.26): a survey of how major management/productivity apps structure navigation and home
screens, and what סיגמה should borrow. Each entry: pattern(s), how it maps to a סיגמה screen, effort.

### Linear
Sidebar is minimal by design ("no busy sidebars, pop-ups, or tabs to manage") with the real workhorse being a
global **Cmd+K command palette** that filters/acts on everything, plus single-letter shortcuts (`C` create,
`E` assign) ([Linear guide, Morgen](https://www.morgen.so/blog-posts/linear-project-management); [command
palette architecture](https://mysites.guru/blog/our-command-palette-navigation-with-cmdk/)).
- **Copy:** a desktop-only `Cmd/Ctrl+K` command bar for עמיחי/עידן — jump to a kibbutz, open a task, start an
  import — nested sub-menus rather than instant-fire, so a wrong keystroke doesn't trigger an action.
- **Maps to:** desktop header search (mockup `desk`/`imp`/`dev` screens) becomes command-capable, not just a
  text filter.
- **Effort: M** (cmdk-style component + action registry; desktop only, skip on phone — field techs don't
  type on a keyboard mid-visit).

### Notion
Sidebar organized into top-level tabs (Home, sections, Favorites, Teamspaces) with **breadcrumbs** showing the
full path on nested pages ([Notion sidebar
help](https://www.notion.com/help/navigate-with-the-sidebar); [breadcrumbs
block](https://www.redgregory.com/notion/2020/3/28/how-to-build-a-navigation-bar-in-notion)).
- **Copy:** breadcrumb trail on drill-down screens that are more than one level deep (e.g. kibbutz card →
  modal tab → meeting-note history → single bullet's linked task) so a technician who followed a chain of taps
  can always see "where am I" and jump back, not just use a back-chevron.
- **Maps to:** kibbutz modal's "🗓 ישיבות" tab and the sub-site (`↳ תת-אתר`) card relationship — a one-line
  breadcrumb ("גבים ‹ תת-אתרים ‹ שכונה חדשה") clarifies parent/child which the mockup currently only shows as a
  badge on the child card.
- **Effort: S.**

### Asana
Redesigned mobile **My Tasks** view plus a Home screen built from widgets (Projects, People, My Priorities) and
a single **global Quick Add** reachable from the top bar everywhere ([Asana Home
features](https://asana.com/features/project-management/home); [mobile My Tasks
redesign](https://forum.asana.com/t/introducing-a-newly-redesigned-my-tasks-on-mobile/593396)).
- **Copy (1):** the "global quick add reachable from anywhere" pattern — one button, not one per screen.
- **Copy (2):** widget-composed home screen for the PM/CEO role specifically (not the field tech role).
- **Maps to:** a floating/header ➕ that's context-aware (on a kibbutz screen → new bullet/task; on מלאי → stock
  report; on קיבוצים home → new kibbutz) rather than the current per-screen ➕ buttons scattered across §7c's
  screens.
- **Effort: M** (needs a small dispatch layer to decide what ➕ means per route — logic exists already, just
  not unified under one control).

### Monday.com
**View switcher** (board/list/calendar/…) is a persistent icon row at the top of every board, and mobile's
**My Work** page has a single "New item" quick-add at top-left ([Monday board
views](https://support.monday.com/hc/en-us/articles/360001267945-The-board-views); [Monday My
Work](https://support.monday.com/hc/en-us/articles/360019300579-My-Work)).
- **Copy:** the calendar's שבוע/חודש toggle (spec §7f already has this, good) should be styled as the same
  persistent switcher pattern, and the same switcher affordance (not a new visual language) should apply to
  the dev page's 🗂/🌳 toggle (§7d) — one consistent "view switcher" component reused everywhere a screen has
  more than one way to look at the same data, instead of three different toggle stylings across calendar/dev.
- **Maps to:** `.tog` component already exists in the mockup CSS — just apply it uniformly (calendar, dev
  board/tree, and any future view switch) rather than risk visual drift per screen.
- **Effort: S** (consolidate an existing style, no new pattern).

### Todoist
**Today view** shows only what's due today across all projects; **natural-language quick add** ("Send the
invoice Friday at 2pm") parses date/priority/project straight out of a typed sentence
([Todoist features](https://www.todoist.com/features); [natural language quick
add](https://www.usecarly.com/blog/how-to-use-natural-language-in-todoist/)).
- **Copy:** the "today, across everything" framing — סיגמה's arrival-day concept is close but scoped to one
  kibbutz; a true **cross-kibbutz "today" view** (today's route stops + today's due tasks + today's missing
  attendance) as an optional home-screen mode would match this pattern.
- **Maps to:** this is effectively what `gapsFor()` (§7h) + `day_plans` (§7f) already compute — the
  recommendation is to *surface* that combined "today" list as a real screen/tab, not just a personal-gaps
  panel buried in settings (ties to recommendation #3 in §1 above — don't bury daily-use views in ⋯).
- **Effort: M** (mostly composition of already-specced data, not new logic).

### Things 3
**Swipe-right to reschedule, swipe-left to select** on a to-do row, with multi-select entered directly from a
swipe rather than an explicit "select mode" toggle ([Things 3
features](https://culturedcode.com/things/features/)).
- **Copy:** swipe actions on EMS task rows and meeting-bullet rows — swipe to "📅 שבץ להיום" (schedule) or "✓
  סיים", instead of requiring the row's own button row to be tapped precisely, which is harder one-handed
  outdoors than a full-width swipe gesture.
- **Maps to:** "✅ משימות" (my tasks) rows already have a button row (📅/✓/📍) per spec §7g — swipe would be an
  *additional* fast path for the single most common action (✓ done), not a replacement, since discoverability
  of swipe gestures is generally weaker than visible buttons for infrequent users.
- **Effort: M** (gesture library + fallback to the existing button row; keep buttons as the discoverable
  path, swipe as the power-user shortcut).

### Trello / ClickUp
Trello's **collapsible board lists** keep a list's name + card count visible while reclaiming board width for
what's expanded, toggled per list, not all-or-nothing ([Trello collapse
list](https://support.atlassian.com/trello/docs/collapse-or-expand-a-list/)).
- **Copy:** this is close to what the dev-page spec (§7d) already specs for minimized columns (`.rc` rail) —
  confirms that decision is on the right track. The one gap: Trello's collapsed list still shows *name + count*
  legibly (horizontal text); see recommendation #8 in §1 — apply Trello's horizontal-collapsed-label approach
  instead of the mockup's rotated text.
- **Maps to:** dev page rail, directly.
- **Effort: S** (already mostly specced; just fix the label orientation per #8).

### Jira mobile
Issue hierarchy (Epic → Story/Task → Sub-task) with **expand/collapse arrows per level** to reveal parent-child
chains without leaving the list ([Jira issue
hierarchy](https://www.tempo.io/blog/jira-hierarchy)).
- **Copy:** same expand/collapse-per-node interaction for the dev page's tree view (§7d "🌳 עץ נושאים") — the
  spec already plans nested rows with indent, this confirms the interaction model (arrow-toggle per root, not
  a single global expand/collapse) is the standard, proven pattern.
- **Maps to:** dev page tree view, directly — no change needed, this is validation the plan is right.
- **Effort: — (already correctly specced).**

### Slack
Redesigned mobile nav from 5 tabs down to a **focused trio** (Home/DMs, Activity, Later), with unread counts as
numbered badges only on tabs that represent triage queues, not on every tab
([Slack mobile redesign](https://slack.design/articles/re-designing-slack-on-mobile/); [unread
badges](https://slack.com/help/articles/19693583638803-Triage-notifications-in-the-Activity-tab)); overflow
items live in a **bottom sheet**, not a nested menu, on Android specifically.
- **Copy (1):** badge numbers belong only on the "things awaiting your action" surface (e.g. ⋯/gaps,
  feedback-inbox for עידן/עמיחי) — never decorative badges on קיבוצים/מלאי just because something changed.
- **Copy (2):** on Android, ⋯ עוד should open as a **bottom sheet** (matches the rest of the app's sheet
  language, spec §6) not a dropdown menu — consistency with the arrival sheet/briefing pattern already chosen.
- **Maps to:** the ⋯ menu (recommendation #3 in §1) — this is the concrete implementation answer to "make ⋯ a
  labeled sheet, not a junk drawer."
- **Effort: S.**

### Google Calendar
Mobile has **no week-number display at all** — only desktop shows it, via a settings toggle, in month view
only, along the left edge of each week ([Google Calendar week numbers,
mobile](https://www.usecarly.com/blog/how-to-show-week-numbers-in-google-calendar/); [Google Calendar view
switching](https://support.google.com/calendar/answer/6110849?hl=en&co=GENIE.Platform%3DAndroid)).
- **Finding, not a copy:** this is useful negative evidence for spec §7f, which puts week numbers on **both**
  phone and desktop calendar views. Google's own product team apparently judged week numbers as
  desktop/power-user-only clutter on a small screen. Recommend: keep week numbers on סיגמה's desktop calendar
  (as specced) but drop them from the phone week/month view — the numbers add cognitive load without action
  value for a technician glancing at "what's today," and the pattern isn't validated on mobile by the market
  leader in this space.
- **Maps to:** spec §7f calendar view, phone variant.
- **Effort: S (remove, don't add).**

### Apple Reminders
**Smart Lists** auto-group items by date/tag/priority/location, and manually-grouped lists can be tapped to
expand into all contained items at once ([Apple Reminders Smart
Lists](https://support.apple.com/guide/iphone/use-smart-lists-iphe882772ed/ios); [grouped
lists](https://www.macstories.net/stories/ios-16-the-macstories-review/12/)).
- **Copy:** the "smart list = a saved filter that looks like a real list" mental model is exactly what
  קיבוצים filter chips (הכל/חדשים/פעילים/שיווקי) and "✅ משימות" filter chips (הכל/באיחור/השבוע/ללא תאריך)
  already do — validates the existing approach, no change needed. One addition worth considering: let עמיחי/
  עידן save a **custom smart list** (e.g. "הקיבוצים שלי בצפון + מאזן פתוח") the way Reminders lets users build
  custom Smart Lists from combined criteria — a "stretch" idea, not required for this release.
- **Maps to:** קיבוצים chips, משימות chips — validated as-is; custom saved filters is a future nice-to-have.
- **Effort: — (validates current plan); custom saved filters would be L, out of scope for this release.**

### Wolt courier / Gett driver
Wolt's courier-partner redesign work specifically called out **low-contrast small text on a busy background**
(order number in light gray on white) as a real field bug fixed by **enlarging text and raising contrast**
under real working conditions — i.e., the same class of problem flagged in §3 of this report (RTL
contrast/outdoor legibility) has already burned a comparable one-thumb, outdoors, on-the-job delivery app
([Wolt Partner app UX
fix](https://blabla.sytyakov.com/ux-refresh-wolt-partner-app/)). Wolt's consumer app additionally uses a
**slide-to-confirm** control instead of a tap-to-confirm button for consequential actions, specifically to
prevent accidental taps in a jostled, one-handed context ([Wolt UX
notes](https://pageflows.com/ios/products/wolt/)).
- **Copy:** slide-to-confirm (or long-press-to-confirm) for the two truly consequential one-tap actions in
  Sigma — issuing a delivery certificate and saving a stock recount with a large negative delta — both are
  currently plain buttons in the mockup, and both are exactly the kind of action a jostled one-handed tap could
  trigger by accident.
- **Maps to:** `.certchip` "🚚 הפק" button (visit screen) and "שמור ספירה מחדש" (inventory recount screen).
- **Effort: S** (swap one button interaction for a slide/long-press variant on two specific screens; not a
  systemic change).

### Fieldwire (construction field app)
Explicitly "field-first" design target: foreman/superintendent using a device with **dirty hands, bad
lighting, spotty cell service**; the app stays fully usable offline (view + add content) and syncs silently
when connectivity returns, with no user-visible offline mode-switching required
([Fieldwire offline design](https://help.fieldwire.com/hc/en-us/articles/202631944-Q-A-Can-I-use-Fieldwire-while-offline);
[field-first philosophy](https://www.constructionperks.com/construction-apps/android/)).
- **Copy:** "offline is not a special mode, it's the default assumption" — directly reinforces recommendation
  #10/§4 of this report (proactive connectivity chrome, optimistic writes) with an external precedent from the
  closest analogous industry (field techs, not office workers, as the primary phone user).
- **Maps to:** every write path in §5 (check-in, visit save, cert issue) and §"מלאי" (stock movements) —
  validates that this report's offline recommendation is not a nice-to-have but the standard bar for
  field-worker software.
- **Effort: — (validates existing recommendation #10/§4).**

### Recommended navigation model for סיגמה

**Phone (field role — אביאם/ניתאי):** bottom nav stays **🏘 קיבוצים · 📍 ביקור (raised) · 🚚 תעודה · 📦 מלאי ·
⋯ עוד**, unchanged from the mockup — it already matches Material 3's 3–5-destination rule and puts the two
highest-frequency actions (visit, cards) most reachable. **יומן/נוכחות/משימות move out of ⋯** into a labeled
bottom **sheet** opened from ⋯ (Slack's Android pattern) — not a second nav row, not a dropdown — with badges
only where something needs action today (gaps, unread feedback reply), never decorative. קיבוצים home gets one
new element: a **"today" strip** at the very top (today's route stops + open gap nudges, Todoist's Today-view
idea applied to our data), collapsible, above the card grid.

**Desktop (עמיחי/עידן/dev):** header search becomes a **Cmd/Ctrl+K command bar** (Linear) for jump-to-kibbutz /
open-task / start-import; view-switcher styling (`.tog`) is unified across calendar week/month and dev
board/tree (Monday.com consistency); breadcrumbs (Notion) appear on any drill-down more than one level deep
(sub-site cards, meeting-note history). Global quick-add is one context-aware ➕ in the header (Asana), not
scattered per-screen buttons.

**What NOT to copy:** Linear's near-zero-sidebar minimalism (סיגמה's phone-first field users need visible
labeled nav, not a command-only interface); Jira's multi-level custom hierarchy (Epic/Feature/Story is
overkill for 6 people); Trello's paid-tier-gated features as a dependency; Google Calendar's mobile week
numbers (drop, don't add, on phone); Wolt's aggressive food-delivery gamification/animation density (motion
budget in §4/§6 already caps this appropriately — don't add more); Slack's full Activity-feed model (סיגמה's
notification surface is intentionally single-nudge per spec §5.2, not a feed to triage).
